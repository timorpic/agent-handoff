# 代码审查

## 适用场景

- 提交前自审，或评审 PR / 补丁，需要给出阻塞项与建议项。
- 怀疑改动超出任务范围、混入无关重构，或验证证据不足。
- 接手他人改动，需要先判断现有实现是否与需求一致。

不适用：需求本身的评审（回到项目需求文档），以及大范围改造的方案讨论
（按详细规则第 15 节的流程处理）。

## 前置读取

- 根目录 [AGENTS.md](../../AGENTS.md)：读取步骤与任务表。
- 详细规则第 5 节（测试与质量）与详细规则第 12 节（完成标准）。
- [docs/DEVELOPMENT.md](../../docs/DEVELOPMENT.md) 的验证命令表：本项目实际使用的检查命令。

## 步骤

1. 固定审查范围：记录基线与目标（如 `git diff --stat <base>...<head>`）；范围不明确时先确认，
   不默认审查整个工作区。
2. 先读被改文件的上文，再看 diff：只看片段容易误判现有行为。
3. 建立映射：把改动逐处对应到需求或验收条目；无法对应的列为待确认，不替作者推断意图。
4. 按四类检查，只报有证据的问题：
   - 正确性：边界、错误处理、状态与并发、空值。
   - 范围：无关改动、顺带重构、格式噪音。
   - 兼容性：对外接口、数据结构、配置项与默认值。
   - 验证：新行为是否有对应测试；哪些检查没有运行。
5. 分级结论：阻塞（影响验收，必须改）/ 建议（可另行处理）/ 提问（信息不足）。
6. 需要时以只读方式执行测试、Lint、构建并记录命令与结果；修复代码另行授权，不顺手改。

## 输出

- 结论：通过 / 有条件通过 / 不通过，一句话说明依据。
- 逐条问题：文件与行号、现象、证据、影响、建议处理方式。
- 验证结果：执行的命令、结果，以及未覆盖的部分。
- 未确认项：需要作者或需求方补充的信息。

不写「已通读全部代码」这类无法核实的表述；没有证据的猜测放「提问」，不放进「阻塞」。

## 验证与记录

- 审查范围（基线、目标提交或工作区状态）、命令与结果随交付说明如实记录，
  逐条审查过程不累积成流水账。
- 反复出现的问题有长期价值时，按详细规则第 13 节记入 [MEMORY.md](../../MEMORY.md)；
  一次性清单不写入长期记忆。

## 边界

- 只做审查，不扩大授权：不提交、不推送、不改他人正在写的文件；需要修改时先取得明确授权。
- 不自动启动、调度或切换其他 Agent；建议不等于已批准的方案。
