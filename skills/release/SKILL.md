# 发版

## 适用场景

- 需要确定下一个版本号，或核对当月/当年序号。
- 准备发版提交、Tag、GitHub Release、包发布或生产部署。
- 发布失败后判断重试方式，或发布后需要核对实际状态。

版本号格式、年度基准、渠道与失败恢复的完整规则见
[docs/AGENT-RULES.md](../../docs/AGENT-RULES.md) 第 17 节；本技能只列执行步骤，不复述规则。

## 前置读取

- 根目录 [AGENTS.md](../../AGENTS.md)：发版相关的任务路由。
- 详细规则第 17 节（Release 发版规则）；涉及部署时另读项目部署文档。
- [MEMORY.md](../../MEMORY.md)：确认发版基准年、时区与版本转换约定。
- [CHANGELOG.md](../../CHANGELOG.md) 与 [docs/DEPLOYMENT.md](../../docs/DEPLOYMENT.md)：
  现有变更说明格式、发布渠道与回滚方式。

## 步骤

1. 确认授权边界：版本提交、Tag、Release、包发布、生产部署是不同操作，
   逐项核对已获授权的事项，不因用户说「发版」就默认全部执行。
2. 核对现场：`git status` 确认没有把他人未提交修改带入发布；确认目标分支与上一版本。
3. 确定版本号：按第 17 节的 vx.MM.xx 计算；用远程 Tag 与 Release 的实际状态确认当月下一序号，
   不只看本地记录，也不复用已公开的版本号。
4. 执行发版前检查：项目要求的测试、类型检查、Lint、构建；存在阻塞失败时停止并说明，不绕过门槛。
5. 整理变更说明：以上一版本到目标提交的实际差异为准，区分功能、修复、破坏性变更与迁移步骤。
6. 按项目既有流程执行；优先使用现有脚本或 CI，不绕过自动化手工发布。
7. 发布后核对远程 Tag、Release、包版本与部署版本；下载或安装产物可用性按需要验证。

## 输出

- 版本号、Tag 名称与对应发布提交。
- 各渠道状态：Tag / Release / 包 / 部署，分别标明成功、失败或未执行。
- 变更说明与升级注意事项。
- 验证结果与仍存在的问题。

部分渠道成功、部分失败时分别报告，不笼统宣称发版成功；「已触发」不等于「已完成」。

## 验证与记录

- 每个渠道的实际状态（含操作 ID 与核查方式）在交付说明中如实记录，
  便于判断是否需要重试。
- 首次发版后把基准年、时区、发布渠道与版本转换约定写入 [MEMORY.md](../../MEMORY.md)；
  只有实际发布成功才记为已发版。
- 跨月跨年或代码修复后需要重新编号的核对过程，随本次交付说明记录。

## 边界

- 不扩大授权：缺少 Tag、Release、包发布或部署授权时，完成可审查的准备工作并停下来说明。
- 已发布的 Tag 与版本号不移动、不覆盖、不删除；需要修复时分配新的当月序号。
- 不为发版强制推送或重写历史；数据库迁移的恢复限制单独核实。
- 不自动启动、调度或切换其他 Agent；发布凭据按项目既有安全机制读取，不写入日志或文件。
