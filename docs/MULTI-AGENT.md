# 多 Agent 客户端接入

> 本文件说明「为什么这样分层」和「各客户端怎么接」，不承载规则正文。
> 规则正文仍在 [AGENTS.md](../AGENTS.md) 与 [docs/AGENT-RULES.md](AGENT-RULES.md)，
> 接入相关的必守边界见详细规则第 19 节；两处冲突时以规则正文为准并修正本文件。
> 本文件不写项目专属事实，也不对任何客户端行为作「已验证」结论。

## 1. 先分清两类结论

阅读本文前先区分证据等级，不要混用：

| 等级 | 含义 | 本环境可否证明 |
| --- | --- | --- |
| A 仓库内自证 | 文件是否存在、相对软链能否解析、脚本能否只读执行 | 可以，随时可复核 |
| B 外部事实 | 某客户端是否加载某文件、何时加载、如何合并多层上下文 | 不可以，属待核实项 |

- A 类结论可当场复核：`ls`、`readlink`、`test -e`、`sh scripts/check-docs.sh`。
- B 类结论一律写「依据官方文档与社区约定，未在本环境验证」或「待核实」；
  写得再具体也不等于实测。接入新客户端后须用一个真实小任务验证（见第 9 节）。
- 客户端版本迭代会改变入口规则，因此本文不写具体版本号，
  也不写未确认的配置键名；需要时先查客户端当前文档再补。

## 2. 设计目标与代价

三条设计彼此独立，各有明确代价，不能当成「免费获得的能力」。

### 2.1 AGENTS.md 作为单一事实来源（SSOT）

- 做法：规则入口只有 [AGENTS.md](../AGENTS.md) 一个，详细正文只有
  [docs/AGENT-RULES.md](AGENT-RULES.md) 一份；客户端入口（如 [CLAUDE.md](../CLAUDE.md)）
  只做定向，不写正文。
- 收益：改一处即对所有客户端生效，不会出现两套规则各自演化。
- 代价：入口必须长期保持薄壳。任何人图省事把正文抄进入口，SSOT 就退化为
  「一处主记录 + N 份副本」，之后必然漂移。
- 边界：SSOT 说明的是**唯一维护位置**，不是自动分发机制。
  引用是读取指令，被引用内容不会因此进入上下文。

### 2.2 `.handoff/` 作为现场接力底座

- 做法：任务目标与授权依据写 `.handoff/CONTEXT.md`，可核验现场写
  `.handoff/CHECKPOINT.md`，跨工具交接按 [HANDOFF.md](../HANDOFF.md) 执行。
- 收益：换工具、换机器、换会话时，接力依据是可观察文件而不是聊天记录。
- 代价：现场层不跟踪 Git，新克隆或换机器时可能不存在；
  缺失时按当前现场重建，不虚构前任记录。
- 边界：现场层是「当前做到哪一步」，不是长期知识。
  长期结论才进 [MEMORY.md](../MEMORY.md)，且现场记录不产生新授权。

### 2.3 分层作用域按需读取

- 做法：全局约束在根入口与详细规则；模块差异写在模块目录的局部 AGENTS.md；
  进入子目录或修改其文件前就近读取。
- 收益：上下文按任务收敛，不必每次加载全部分层。
- 代价：分层依赖执行工具真的去读——「文件存在」不等于「已加载」。
- 边界：局部入口只补充、不覆盖；不得复制规则正文，也不记录进度与测试结果。

## 3. 目录与职责映射

「谁读它」是仓库约定，不是对客户端行为的实测；
「进 Git」一栏的细则见 `docs/INITIALIZATION.md`「模板文件的 Git 跟踪策略」（该文件仅存在于模板仓库）。

| 路径 | 职责 | 谁读它 | 进 Git |
| --- | --- | --- | --- |
| [AGENTS.md](../AGENTS.md) | 启动入口、必守边界、章节读取路由 | 所有客户端（入口步骤） | 是（项目层） |
| [CLAUDE.md](../CLAUDE.md) | Claude Code 薄壳入口，只定向到 AGENTS.md | Claude Code 会话 | 是（入口层，可适配） |
| [MEMORY.md](../MEMORY.md) | 长期事实与已确认决策的主记录 | 每次会话的身份与事实核对 | 是（项目层） |
| [HANDOFF.md](../HANDOFF.md) | 人工接力协议 P0+P1 | 交接、接管与异常恢复 | 是（协议层，项目内禁改） |
| [PROMPTS.md](../PROMPTS.md) | 初始化、交接、接管与恢复的提示词 | 由用户复制使用 | 是（协议层，项目内禁改） |
| `.handoff/CONTEXT.md`、`.handoff/CHECKPOINT.md` | 当前任务、范围、现场与验证证据 | 每次会话与每次接管 | 否（现场层） |
| `.handoff/archive/**` | 冻结的历史上下文与检查点 | 需要追溯旧现场时 | 是（项目层） |
| [docs/AGENT-RULES.md](AGENT-RULES.md) | 详细工作规则正文，按章节稳定引用 | 按任务表读取适用章节 | 是（协议层，项目内禁改） |
| docs/decisions/ | 架构决策记录（ADR-001-xxx.md） | 需要核对取舍理由时（按需建立） | 建立后是 |
| docs/runbooks/ | 部署、运维与排障手册的实际步骤 | 执行运维操作前（按需建立） | 建立后是 |
| [skills/README.md](../skills/README.md)、`skills/<name>/SKILL.md` | 可复用工作流说明 | 按需读取单个技能 | 是（项目层） |
| `.claude/settings.json` | 客户端私有权限配置，不含凭据 | 客户端读取；人审阅 | 是（平台配置） |
| `.claude/skills` | 指向 `../skills` 的相对软链 | Claude Code 技能发现 | 是（只跟踪链接本身） |
| `.gemini/antigravity/skills` | 指向 `../../skills` 的相对软链 | Antigravity 技能发现 | 是（只跟踪链接本身） |
| `.claude/memory/`、`.gemini/antigravity/scratch/` | 客户端临时缓存与会话草稿 | 客户端自身 | 否（按目录忽略） |
| tools/ | 项目自有维护脚本与长提示词模板（按需建立） | 执行具体检查或生成时 | 是（源码；产物按项目约定） |
| src/ | 项目源码（按需建立） | 实现任务 | 是（项目层） |

补充说明：

- ADR 的统一位置是 `docs/decisions/`，文件名形如 `ADR-001-xxx.md`；
  与初始化说明的「按需增加的文档」一节一致（该说明仅存在于模板仓库），不在项目内并存两套目录。
- 表中标「按需建立」的目录不存在是正常状态，不预建空目录，也不写占位文件。
- 平台目录不得整体忽略，否则会连配置与技能一起丢失；只按锚定路径忽略缓存子目录。

## 4. 客户端映射矩阵

列含义：**默认识别入口**是客户端侧的约定（B 类）；**本项目适配**是仓库内已经做好的事（A 类）；
**核实状态**说明该行结论的可靠程度。

| 客户端 | 默认识别入口 | 本项目适配 | 上下文边界控制 | 核实状态 |
| --- | --- | --- | --- | --- |
| Claude Code | CLAUDE.md（B 类） | [CLAUDE.md](../CLAUDE.md) 为薄壳；可整体替换为指向 AGENTS.md 的相对软链，或合并保留项目专用内容；进入子目录时按需读取该目录及上级的局部 AGENTS.md | 靠子目录就近叠加与按需读取，不预加载全部技能 | B：依据官方文档与社区约定，未在本环境验证。A：CLAUDE.md 存在且不含规则正文 |
| Codex | AGENTS.md（B 类） | 直接使用根 [AGENTS.md](../AGENTS.md) 作为指令源，不另建专用入口；局部目录就近叠加 | 按目录就近叠加；详细规则按章节读取 | B：依据官方文档与社区约定，未在本环境验证。A：AGENTS.md 存在且分层规则已写入 |
| OpenCode | AGENTS.md（B 类） | 同上；全局或用户级配置保留在用户自己的 `~/.config/opencode/`，仓库内不写个人路径与个人凭据 | 项目内只保留仓库相对路径的引用 | B：待核实（配置目录与入口均未在本环境验证） |
| DeepSeek Harness | AGENTS.md（B 类） | 直接读取根入口；按需读取 `.handoff/CONTEXT.md` 与 `.handoff/CHECKPOINT.md` | 现场层按需读取，不整篇注入历史 | B：依据官方文档与社区约定，未在本环境验证。A：仓库内相关文件存在 |
| Antigravity / Gemini | `.gemini/antigravity/skills`（B 类） | 软链共享根 `skills/`（A 类可验证）；入口文件按客户端当前版本核实后再补，不凭印象写 | 技能按需读取单个 SKILL.md | B：入口文件待核实。A：`readlink` 输出 `../../skills` 且 `test -e` 通过 |

新增客户端时补一行，并写清核实依据（文档链接、实测日期或「未验证」）。
未实测的行为只能写「待核实」，不能因 README 或社区文章写过就当作事实；
与仓库约定冲突时先核实再改，不按文件新旧取舍。

## 5. 分层作用域

### 5.1 读取顺序

1. 仓库根 AGENTS.md 与本次任务适用的详细规则章节。
2. 进入目标子目录后，读取该目录及上级目录的局部 AGENTS.md。
3. 局部入口指向的模块文档（架构、边界、验证命令）。
4. 冲突时以限制更严格的一方为准；无法判断时先核实，不自行放宽。

### 5.2 什么时候需要局部 AGENTS.md

满足任意一条才建；都不满足就不建，避免空白入口满地都是：

- 存在模块级差异约束：数据访问边界、依赖方向、命名或目录约定。
- 有模块专用的验证入口，且与根文档的命令不同。
- 该目录有独立发布或独立授权边界。
- 目录内文件经常被跨模块改动，需要就地提醒边界。

反过来，只是多层目录、几个文件，或差异能用一句通用规则覆盖时不需要——写进根入口或详细规则即可。

### 5.3 局部入口的写法

- 只写本模块实际存在的差异，不复制通用规则，不记录进度与测试结果。
- 局部目录的 `CLAUDE.md` 用相对软链指向同级 `AGENTS.md`，不另写正文。
- 模板见 [adapters/scoped/MODULE-AGENTS.md](../adapters/scoped/MODULE-AGENTS.md)，
  复制后替换占位符，并同步更新链接。
- 不支持软链的平台写一个短指针文件，内容只说明「读取同级 AGENTS.md」，不复述规则。

### 5.4 软链失效时的回退

| 场景 | 回退形态 |
| --- | --- |
| Windows 无创建软链权限 | 建同名目录，内放 `README.md` 指针，写明共享位置，不复制正文 |
| `core.symlinks=false` 的检出 | 链接被检出为普通文本文件，按内容重建为真链接 |
| 平台完全不支持链接 | 指针文件 + `AGENTS.md` 步骤说明，二者都只做定向 |

回退只改变「怎么找到目标」，不改变「正文只维护一份」。
初始化脚本创建链接失败时应给出明确提示并回退，不静默跳过。

## 6. 技能共享

- 标准位置是根目录 `skills/<name>/SKILL.md`，一个目录一份，不按客户端分叉。
- 客户端私有目录用相对软链指过来：`.claude/skills -> ../skills`、
  `.gemini/antigravity/skills -> ../../skills`。
- 相对路径按**链接所在目录**解析：`.gemini/antigravity/skills` 写成 `../skills`
  会解析为 `.gemini/skills`，指向不存在的目录且创建时不报错，属静默失效，只能靠事后 `test -e` 发现。
- 软链本身要进 Git（符号链接模式 120000），否则新克隆后客户端看不到技能。
- frontmatter 只保留必要字段：`name` 必须等于所在目录名，改名即断链；
  `description` 用一行写「何时使用」，写触发场景而不是罗列功能。
- 正文写步骤、输出与验证要求；需要规则约束时引用章节号，不复制规则正文。
- 不支持项目级技能的客户端，按 [AGENTS.md](../AGENTS.md) 第 5 步
  直接读取 `skills/<name>/SKILL.md`，不为此另建规则副本。
- 技能是工作流说明，不是授权来源：不扩大授权，也不构成自动调度。

仓库内可自证的检查（A 类）：

~~~sh
readlink .claude/skills              # 期望 ../skills
readlink .gemini/antigravity/skills  # 期望 ../../skills
test -e .claude/skills && test -e .gemini/antigravity/skills && echo ok
~~~

## 7. 上下文边界与成本

按读取时机分三类，不要混为一谈：

| 类别 | 内容 | 说明 |
| --- | --- | --- |
| 每次会话必读 | 适用的 AGENTS.md、本次任务适用的详细规则章节、MEMORY.md 中的身份与现行事实、CONTEXT 与最新 CHECKPOINT（如存在） | 缺现场层时按当前现场重建，不虚构 |
| 按任务读取 | 需求、架构、ADR、运行手册、单个 SKILL.md、归档检查点 | 按 CONTEXT 的精确引用取用，不做全量遍历 |
| 不自动注入 | 历史归档、全部技能正文、完整测试日志、聊天记录、模型内部状态 | 需要时再显式读取 |

两条容易被忽略的事实：

- **文件存在 ≠ 自动注入**：入口写了「请读取 X」，不代表 X 已在上下文里。
  执行工具必须真的读，读了才可引用。
- **引用 ≠ 已读取**：链接、章节号、技能名都只是定位符；
  输出被截断时补读，不声称已读取未见内容。

成本控制的做法是「按章节与按需读取」，不是机械截断条目，
也不假设某个模型的具体 token 配额；整理文档以定位方便为准。

## 8. 避坑清单

| 现象 | 后果 |
| --- | --- |
| 相对软链层级写错（`.gemini/antigravity` 下写 `../skills`） | 指向 `.gemini/skills`，创建成功但技能永远发现不了，属静默失效 |
| 把入口做成副本、把规则抄进 CLAUDE.md 或局部 AGENTS.md | 出现多套规则，改动只落在一处，后续必然漂移 |
| 把 `.handoff/` 现场层提交进 Git | 别人的会话进度被当成项目事实，交接冲突且污染历史；模板仓库的空白模板是唯一例外 |
| 依赖客户端自带会话记忆替代 MEMORY.md | 记忆内容不可审计、不可跨工具继承，冲突时无法判断依据 |
| 直接在 `.claude/skills` 目录本体放技能 | 其他客户端看不到同一份技能，形成事实上的单体绑定 |
| Windows 下软链退化为目录或复制 | 内容分叉；必须用目录 + 指针文件，且指针不复述正文 |
| `core.symlinks=false` 检出后链接变文本文件 | 客户端读到的是一行路径文本而非目标内容，需按内容重建链接 |
| 只写入口不复核 | 入口写了却没人读，规则实际上没生效；接入后必须实测一次 |

## 9. 验证方式

改动入口、技能或作用域后，按顺序做以下检查；
前两项是仓库内可执行的 A 类检查，最后一项依赖真实客户端。

1. `sh scripts/check-docs.sh`（仓库根执行，只读）：覆盖 Markdown 死链与章节引用，
   并按脚本头注释实际列出的检查项扩展（技能前置元数据、软链解析等属扩展项，
   以脚本实际实现为准，不以文档描述为准）。失败时逐条定位，
   区分布局原有问题与本次引入的问题。
2. `node scripts/init.mjs --dry-run`：只打印生成计划，不写盘；
   用于确认新项目会拿到哪些文件、哪些引用会被替换。
3. 软链与技能元数据的定点核对：`readlink`、`test -e`，
   以及 frontmatter 的 `name` 是否等于目录名。
4. 新项目接入后先用一个**小任务**验证入口确实被读取：
   观察执行工具是否引用了入口步骤与适用章节；没有加载时改用
   [PROMPTS.md](../PROMPTS.md) 中的显式提示，再记录实际结果。
5. 记录结论时区分「通过」「失败」「未运行」「验证受阻」，
   不把触发操作当成完成，也不把未实测的外部行为写成已验证。

多客户端并存不改变既有边界：同一工作区仍只有一位写入者，
仍由用户手动切换工具，不自动调度、不轮询、不并行写入。
